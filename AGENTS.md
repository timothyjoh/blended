# Repository Guidelines

## Project Structure & Module Organization
`src/` holds application code: page shells live in `src/pages`, shared UI in `src/components`, layout wrappers in `src/layouts`, domain logic and utilities in `src/lib`, and styling tokens in `src/styles`. Content collections (e.g., blog posts) live in `src/content`, while long-form references sit under `docs/`. Static assets ship from `public/`, and Tailwind configuration is centralized in `components.json`.

## Build, Test & Development Commands
Use `npm install` to sync dependencies. `npm run dev` starts the Astro dev server with hot reload. `npm run build` compiles the production site to `dist/`, and `npm run preview` serves that build for smoke-testing. `npm run astro check` runs Astro's type and content safety checks; call it before opening a pull request.

## Coding Style & Naming Conventions
Stick to modern TypeScript/JS without semicolons and two-space indentation, mirroring existing files. Favor `.astro` files for composition and `.tsx` React islands for interactive widgets. Co-locate feature assets (images, partials) with their component or page. Tailwind utility classes are preferred over ad-hoc CSS; keep custom styles in `src/styles` when utilities fall short.

## Data Layer (Blended event spine)
`src/lib/db.ts` is the **single** place that initializes the InstantDB client and defines the Blended `i.schema` (entities `users`, `sessions`, `sessionResources`, `participants`, `sessionEvents`, `messages`, `questions`, `endorsements`). Product code imports the `db` client and schema-derived types from this module — do not call `init()` or redeclare schema elsewhere. It throws at module init if `PUBLIC_INSTANTDB_APP_ID` is missing rather than building a broken client.

**All product mutations MUST route through `writeEvent(type, meta, projectionTxns)`** (ADR-0001, ADR-0003). It appends a SPEC §7.2 `sessionEvents` envelope **and** applies the caller's projection update(s) inside one `db.transact()`, so the event log and projections stay consistent and every interaction is replayable. No product code path may write a Blended projection row (`db.tx.<entity>[…].update/delete`) outside the helper — a projection-only write is a bug (the legacy `todos` demo is exempt). `applyEvent` / `rebuildSessionProjection` in the same module fold an ordered event list back into a projection (SPEC §17.1) and surface unknown event types loudly. InstantDB entity ids must be UUIDs (use `id()` re-exported from `@/lib/db`).

The dev-only scratch harness `/dev/event-spine` (`src/components/EventSpineHarness.tsx`) exercises the dual-write path for two event types and renders the live event/projection rows; it is disabled in production builds. Under the permission rules below it writes as the **signed-in** user (sign in at `/login` first), so its session/participant rows are owned by `user.id`. If writes are rejected with a schema error, push the schema to the Instant app with **`npm run schema:push`** (the fail-loud wrapper).

### Deploy prerequisite runbook (push order)
Before deploying against a schema-enforced live Instant app, push the schema and perms with the **canonical single command**:

```sh
npm run db:push
```

`db:push` (`scripts/push-db.mjs`, cycle 0022) runs the two pushes **in the one correct order** — `schema:push` first, then `perms:push` **if and only if** the schema step exited 0 — so the ordering and stop-on-failure semantics are an enforced, executable property rather than a ritual the operator must remember. A schema-step failure halts the run non-zero with `db:push: schema step failed (exit N) — halting; perms NOT pushed …` and the perms push is **never** attempted; a perms-step failure surfaces `db:push: perms step failed (exit N)`. The first non-zero exit is forwarded, never collapsed to 0. The full operator procedure (auth → env → `db:push` → credentialed `e2e/permissions.spec.ts` to 0-skipped) is in **`docs/runbooks/db-push.md`**.

The two underlying commands remain the documented **building blocks** `db:push` composes (run them individually only to debug a single half):

1. **`npm run schema:push`** — push the committed `src/lib/db.ts` schema (entities, links, accreted additive attrs) to the live app. Run **first**. Until this runs, a schema-enforced app **rejects every `writeEvent()` transaction** and the product stops working.
2. **`npm run perms:push`** — push the permission rules. Run **only after** a successful schema push.

**Order rationale:** the perms rules reference schema-defined links/attrs (e.g. `data.ref('participant.userId')`, `data.ref('session.teacherId')`), so those refs only resolve once the schema is live — schema **first**, then perms. All three commands are **fail-loud** (non-zero on missing app id / un-spawnable CLI / CLI auth/network rejection, each with a distinct actionable message) and **idempotent** (declarative `instant-cli push`; re-running an unchanged schema/ruleset is a safe no-op). They consume `PUBLIC_INSTANTDB_APP_ID` and an authenticated `instant-cli login` session; absent these they fail loudly rather than leaving the live app unmigrated while reporting success.

### Permission rules / data-layer authorization
`src/lib/perms.ts` is the **single source** of the InstantDB permission rules (cycle 0003); the root `instant.perms.ts` is only a CLI adapter that re-exports it (what `instant-cli push perms` loads). The rules enforce two SPEC invariants at the data layer so they hold even against a hand-crafted client, not just the UI:

- **`users` is own-row-only** (`view/create/update = auth.id == data.id`, `delete = false`). The canonical **private email lives ONLY here** — no client can read another user's row, so no email leaks. The `users` row id IS the auth id, so first-sign-in creation stays permitted.
- **`sessions` and `sessionResources` are owner-only writes** (`auth.id == data.teacherId`) with **open reads** (students must follow the lesson). This protects session lifecycle and the `activeResourceId` projection (and the later `currentUrl` field, which inherits the same policy). `sessionResources` carries a denormalized `teacherId` (mirrors `sessions.teacherId`) so ownership is checkable without link traversal — future `writeEvent` resource creators MUST populate it.
- **`sessionEvents` is append-only by any authenticated participant** (`create = auth.id != null`, no client `update`/`delete`) — keeps `writeEvent()` legal, including first-sign-in identity writes.
- **`participants` carry NO email** — InstantDB view rules are row-level, not column-level, so email privacy is structural: the field is removed from the entity, not masked by a rule. **Owner-scoped writes (cycle 0007, resolving the former fail-open hole):** `create/update/delete = isOwnRow || isSessionOwner || isAdmin`, where `isOwnRow = auth.id == data.userId` (a student manages only their OWN row — which is what a legitimate self-join sets), `isSessionOwner = auth.id in data.ref('session.teacherId')` (the owning teacher, checked against the LINKED parent session via the new `participantSession` link, forgery-proof exactly like `sessionResources`), and `isAdmin = false` (reserved client-admin slot). Reads stay open so presence/roster is visible. A signed-in user can no longer mutate or delete a participant row they don't own.
- **System/admin** actions run through `@instantdb/admin`, which **bypasses** these rules; the future client-side admin slot is reserved by the `isAdmin` bind (`false` today, ADR-0003 `User.adminLevel`).
- **Deny by default (cycle 0013).** The global `$default` rule **denies every op** (`allow: { $default: 'false' }`): any entity WITHOUT an explicit block — including any future schema entity and any undeclared namespace — is non-readable and non-writable by a client. **Every new schema entity MUST ship with its own explicit permission rule** (the structural guard in `src/lib/perms.test.ts` iterates `schema.entities` and fails loudly if any lacks one, or if `$default` is ever loosened back to `'true'`). The namespaces that previously relied on the permissive default now carry explicit blocks: `todos` (demo) and the Batch-2 namespaces `questions` / `endorsements` stay intentionally open (`allow: { $default: 'true' }`), their real participant/owner-scoped read+write policy a deferred follow-up. **`messages` was tightened in cycle 0014** — it no longer carries an open `$default`; it has explicit `view`/`create`/`update`/`delete` clauses (participant-scoped create + row-owner/owning-teacher update/delete; see the Student-chat note below). Openness is now a visible, reviewable decision — never silent inheritance.

Push the rules with **`npm run perms:push`** (a fail-loud wrapper around `npx instant-cli push perms` — exits non-zero with a clear message on missing app id or CLI/auth/network failure; idempotent, safe to re-run), after **`npm run schema:push`** so the schema delta (`sessionResources.teacherId`, removed `participants.email`, etc.) is live first (see the deploy runbook above for the ordering rationale). The rules' semantics are pinned by a structural unit test (`src/lib/perms.test.ts`) and proven end-to-end against the live app by `e2e/permissions.spec.ts` (skips loudly without `INSTANT_ADMIN_TOKEN`).

**Auth** is reached through one shared hook: `useAuth` (`src/lib/useAuth.ts`) wraps `db.useAuth()` + the magic-code auth namespace and exposes `{ user, isLoading, error, username, sendCode, verifyCode, signOut }`. Product code MUST NOT call `db.useAuth()` directly outside this hook — all auth state flows through `useAuth` so later cycles consume identity from one place. The signed-in view shows the derived `username` (email local-part), never the raw email (SPEC §40). First-sign-in `users`-row creation goes through `writeEvent()` under the reserved `IDENTITY_SCOPE` sentinel sessionId (`src/lib/auth.ts`) with actor role `'unknown'` and a `UserSignedIn` event — guarded by `shouldCreateUserRow` so it is idempotent across reloads and repeat sign-ins. `UserSignedIn` is intentionally OUTSIDE the session fold: `applyEvent` throws `UnknownEventTypeError` on it by design (identity events belong to no real session). The product sign-in surface is `/login` (`src/pages/login.astro` → `src/components/AuthGate.tsx`).

**Route guarding** (cycle 0004): `RouteGuard` (`src/components/RouteGuard.tsx`) is the SINGLE client-side gate for protected islands — it consumes `useAuth` (never `db.useAuth()`) and resolves four states: `route-guard-loading` (auth unresolved — never redirects, avoiding a flash-redirect), an unauthenticated bounce to `/login?next=<encoded dest>` via `window.location.replace`, `route-guard-denied` (auth error or failed ownership check — logged via `console.error`, never collapsed to "authenticated"), and the rendered children. Guarding is client-side by design because auth state is client-held (SSR pages render a shell that hydrates and decides); there is no server/middleware protection. `safeNextPath` (`src/lib/routing.ts`) is the ONLY sanctioned way to resolve a post-login destination — it honors a `next` only when it is a same-origin absolute path, otherwise falling back to `/dashboard`, so a crafted `?next=` cannot drive an open redirect; `AuthGate` calls it after sign-in (and routes an already-signed-in `/login` load to `/dashboard`). Ownership-scoped routes use `SessionRouteGuard` (`src/components/SessionRouteGuard.tsx`), which runs the `sessions` `db.useQuery` and folds the result through the pure `authorizeOwnership` helper (`session.teacherId === user.id`) into a precomputed `authorize` decision passed to `RouteGuard` (hooks can't run inside a predicate closure). `/dashboard` and `/dashboard/sessions/[id]` are placeholder shells only (real screens are later cycles). Fixed testids for downstream cycles: `route-guard-loading`, `route-guard-denied`, `dashboard-root`, `session-root`.

**Session creation** (cycle 0005): sessions are created via `createSession` (`src/lib/sessions.ts`), the only sanctioned create path — it routes the dual-write through `writeEvent('SessionCreated', …)`, so the `SessionCreated` envelope and the `draft` `sessions` projection row commit in one transaction (a rejected create leaves no partial state). The module keeps the auth.ts-style pure-core split: `generateJoinCode` is the sanctioned **unguessable** join-code source (length `JOIN_CODE_LENGTH` = 10 over the unambiguous charset `JOIN_CODE_ALPHABET`, crypto-backed with an injectable RNG for deterministic tests), and `buildSessionCreate` totally validates input (rejects blank/whitespace title and missing `teacherId` BEFORE producing any txn) and builds the record + envelope meta (`actor.role: 'teacher'`, `sessionId === payload.id`). `createSession` is NOT idempotent by design (each call mints a fresh `sessionId`/`joinCode`). The dashboard control is `NewSession` (`src/components/NewSession.tsx`), a nested island inside `RouteGuard` that reads identity via `useAuth` — **creating a session is what makes a user its teacher** (a session-scoped role, not an account type; any signed-in user may create one). Fixed testids downstream cycles reuse: `new-session-open`, `new-session-title`, `new-session-submit`, `new-session-error`, `created-session`, `created-session-title`, `created-session-status`, `created-session-joincode`, and (cycle 0006) `created-session-link` (the post-create link to the detail page). The e2e seam adds a Node-side admin read helper `queryAdmin` (`e2e/support/auth.ts`) for observability assertions.

**Session lifecycle** (cycle 0006): a created `draft` session is moved through its lifecycle via `startSession` / `endSession` (`src/lib/sessions.ts`) — the ONLY sanctioned transition paths — which route the dual-write through `writeEvent('SessionStarted', …)` / `writeEvent('SessionEnded', …)`, so each lifecycle envelope and the `sessions` projection update (status + `startedAt`/`endedAt`, SPEC §5.2) commit in one transaction (a rejected transition leaves no partial state). The legal-transition guard `assertLegalTransition` is the single source of SPEC §6.2 truth: `draft → live` (start) and `live → ended` (end) are the ONLY permitted transitions this cycle; every other (`draft → ended`, `live → live`, `ended → *`, `archived`, unknown/missing status) throws BEFORE any write. The pure builders `buildSessionStart` / `buildSessionEnd` totally validate the transition AND owner identity (`actorId === session.teacherId`, `actor.role: 'teacher'`) AND a present `sessionId` before producing any plan — ownership is enforced in depth (builder + `SessionRouteGuard` + the cycle-0003 data-layer rule `auth.id == data.teacherId`). Fed the LIVE status, the guard is also the stale-tab / duplicate-event protection: a re-issue on an already-transitioned session is rejected, not deduped (`startSession`/`endSession` are NOT idempotent by design). `applyEvent` (`src/lib/db.ts`) now folds `SessionStarted` / `SessionEnded` (status → `live`/`ended`), so the log still rebuilds the projection and neither type raises `UnknownEventTypeError`. `isJoinEnabled(session)` (`src/lib/sessions.ts`) is the sanctioned join gate — pure and total, `true` ONLY when `status === 'live'`. The detail-page island is `SessionLifecycle` (`src/components/SessionLifecycle.tsx`), mounted inside `SessionRouteGuard` on `/dashboard/sessions/[id]`; it reads identity via `useAuth` and the live session via `db.useQuery`, derives the join affordance solely from `isJoinEnabled`, and surfaces any failed/illegal transition inline (`role="alert"`) + `console.error` — never swallowed. Fixed testids downstream cycles reuse: `session-start`, `session-end`, `session-status`, `session-join-state`, `session-lifecycle-error` (the `session-root` container testid is retained for the ownership-guard e2e).

**Student join (cycle 0007):** a student enters a live session through `/join/:joinCode`. `joinSession` / `buildParticipantJoin` (`src/lib/sessions.ts`) are the **sole sanctioned participant-create path** — `buildParticipantJoin` totally validates input (present `sessionId`, present `userId`, non-blank derived `username`) BEFORE producing any plan, and `joinSession` routes the dual-write through `writeEvent('ParticipantJoined', …)` so the envelope and the `participants` projection row (`role: 'student'`, local-part `username`, `joinedAt`/`lastSeenAt`, `chatStatus: 'allowed'`, plus the `session` ownership link) commit in one transaction (a rejected join leaves no partial row); no projection-only `participants` write exists in product code. The `username` is the email **local-part only** (`deriveUsername`, SPEC §12.3); **participant rows carry no email by design** (privacy is structural). Unlike create/lifecycle, **`joinSession` is idempotent per (user, session)**: the join island pre-checks the live `participants` count via the pure `shouldCreateParticipant` (mirroring `shouldCreateUserRow`) plus an `inFlight` ref latch, so a reload for an already-joined user routes straight in with no second row. `buildParticipantJoin` keeps `participantId === record.id === payload.participantId` so the `ParticipantJoined` fold in `applyEvent` reproduces the same row. The islands are `JoinSession` (`src/components/JoinSession.tsx`, mounted in `RouteGuard` on `/join/[joinCode]` — unauthenticated visitors bounce to `/login?next=/join/<code>`; eligibility derives solely from `isJoinEnabled`; unknown/non-live/error states are non-blank and logged, routing to `/s/<code>` on success) and the read-only live-syncing `StudentSession` (`src/components/StudentSession.tsx`, `/s/[joinCode]`, proving late-joiner sync via `db.useQuery` over the session + its participants). The `participants` permission rules were tightened from fail-open to owner-scoped in this cycle (see the Data Layer note above; the new `participantSession` link makes teacher ownership forgery-proof). Fixed testids downstream cycles reuse: `join-root`, `join-loading`, `join-not-found`, `join-not-open`, `join-error`, `student-session-root`, `student-session-status`, `student-session-presence` (and per-row `student-session-presence-item`). The e2e suite is `e2e/join-via-link.spec.ts` (multi-context A/B/C late-joiner + failure legs; skips loudly without admin env).

**Student chat (cycle 0008):** a joined student participates by sending chat messages from the student session view (`/s/:joinCode`). `submitChatMessage` / `buildChatMessage` (`src/lib/sessions.ts`) are the **sole sanctioned message-create path** — `buildChatMessage` totally validates input (present `sessionId`, present `participantId`, present `userId`, present `clientActionId`, non-blank trimmed `text`) BEFORE producing any plan, and `submitChatMessage` routes the dual-write through `writeEvent('ChatMessageSubmitted', …)` so the envelope (`actor.role: 'student'`) and the `messages` projection row (`visibility: 'visible'`, `classificationStatus: 'unclassified'`, plus the `session` link) commit in one transaction (a rejected submit leaves no partial state); no projection-only `messages` write exists in product code. **Idempotency is by client action id**: the `messages` row id IS the `clientActionId` (`record.id === clientActionId === payload.messageId`), a deterministic keyed upsert, so a repeated logical submit collapses to one row — the island pre-checks via the pure `shouldSubmitChatMessage` (mirroring `shouldCreateParticipant`) plus an `inFlight` ref latch and a per-submit `currentActionId` ref (cleared on success, retained on failure for retry). The schema delta this cycle adds `messages.clientActionId` (indexed) + the `messageSession` link; `applyEvent` now folds `ChatMessageSubmitted` into a `messages` map (defensive defaults, keyed by `messageId`) so neither the type raises `UnknownEventTypeError` nor the fold breaks `rebuildSessionProjection`. **`messages` is participant-scoped as of cycle 0014** (`src/lib/perms.ts`, no longer fail-open). **READ stays open** (`view: 'true'`, intentional — the live cross-student stream depends on every client reading every session's chat). **CREATE is participant-scoped AND anti-spoof**: a row is creatable only when the author owns the LINKED participant (`auth.id in data.ref('participant.userId')`, forgery-proof via the new `messageParticipant` link) AND the stored `participantId` scalar equals that linked participant's id (`data.participantId in data.ref('participant.id')`) — so a client cannot attribute a message to a participant it does not own, whether by setting a foreign scalar or by decoupling the scalar from the link. **UPDATE/DELETE** are restricted to the authoring participant, the owning teacher (`auth.id in data.ref('session.teacherId')`, checked against the LINKED session — never a client field), or the reserved `isAdmin` slot (false today; the admin SDK bypasses rules) — mirroring the `participants` row-owner + owning-teacher pattern. The sole sanctioned send path sets the `messageParticipant` link (`defaultChatTxn` → `.link({ session, participant })`), so legitimate student sends satisfy the create rule; `questions` / `endorsements` remain the open Batch-2 namespaces. **This cycle DOES push**: the additive `messageParticipant` link via `npx instant-cli push schema` (schema-first, so `data.ref('participant.*')` resolves), then the tightened rules via `npm run perms:push`. The island is `StudentChat` (`src/components/StudentChat.tsx`), mounted beside `StudentSession` in `RouteGuard` on `/s/[joinCode]`: a single natural-text input (no message-type selector, SPEC §9.1) + a realtime-syncing stream (`db.useQuery` over `messages` by `sessionId`, sorted client-side by `createdAt` then `id`), gated so input is enabled only when `isJoinEnabled(session)` AND the caller's participant `chatStatus === 'allowed'`; query/submit errors surface inline (`role="alert"`) + `console.error('[StudentChat] …')`, never swallowed. The stream renders the participant `username` (local-part) only — **messages carry no email**. **Teacher exclusion (SPEC §9.3):** the teacher facilitation view (`SessionLifecycle` on `/dashboard/sessions/[id]`) deliberately mounts NO chat island — the teacher works from curated Questions, not the raw stream. Fixed testids downstream cycles reuse: `student-chat-root`, `student-chat-input`, `student-chat-send`, `student-chat-stream`, `student-chat-message-item`, `student-chat-error` (plus `student-chat-disabled` for the not-eligible state). The e2e suite is `e2e/student-chat.spec.ts` (realtime B→C, late-joiner D, teacher exclusion, dual-write counts, idempotency, blank-failure; skips loudly without admin env). **Schema push:** `messages.clientActionId` + the `messageSession` link are additive — run `npx instant-cli push schema` before the feature works against a schema-enforced live app.

**Message → Question promotion (cycle 0009):** the FIRST cycle that produces the teacher-facing `Question` object. The classification decision lives behind a **single, pure, total seam** — `classifyMessage(text) -> { isQuestion: boolean }` (`src/lib/classify.ts`) — implementing the interim, AI-free trailing-`?` heuristic (`isQuestion` true iff the trimmed text ends with `?`; `null`/`undefined`/empty/whitespace → `false`, never throws). **This is the ONE point Batch 2 swaps for an AI call** — there is NO inline `endsWith('?')` anywhere in the submit path, the component, or the fold, so the swap touches only `classifyMessage`'s body. After the `ChatMessageSubmitted` write succeeds, `submitChatMessage` (`src/lib/sessions.ts`) classifies the stored text and, when question-like, issues a **SECOND** `writeEvent('QuestionCreated', …)` dual-writing the `questions` projection row + event in one transaction (atomic — a Question failure leaves no orphan row/event); it is issued only AFTER the message commits, so a failed Question write leaves the message chat-only and the rejection propagates to the caller (logged/surfaced by `StudentChat`), never swallowed. The `questions` row id is **deterministically derived from the source `messageId`** via the pure, bijective `deriveQuestionId(messageId)` (XOR with a fixed 16-byte namespace that preserves the v4 version/variant bits) — so a logical re-submit re-upserts the SAME Question row (keyed-upsert idempotency, mirroring the message). The pure `buildQuestion(plan)` derives the row + envelope (`actor.role: 'student'`, payload `{ questionId, messageId, participantId, sessionId, status, createdAt }`) from the `ChatMessagePlan`; the row links to its source `messages`, author `participants`, and `sessions` rows via the new `questionMessage`/`questionParticipant`/`questionSession` links (forward `one`/reverse `many`, mirroring `messageSession`) and carries **no email** (privacy stays structural). `applyEvent` now folds `QuestionCreated` into a `questions` map (defensive defaults — `status` → `'submitted'`, `createdAt` → `occurredAt`, `sessionId` → projection's; keyed by `questionId ?? event.id`) so the type never raises `UnknownEventTypeError` and `rebuildSessionProjection` stays whole. **No teacher-facing Question UI this cycle** (Questions are created but not yet surfaced to the teacher — a subsequent issue). **`messages`/`questions` were left at the open default this cycle** — **no `perms:push` this cycle** (as of cycle 0013 both carried their own explicit `allow: { $default: 'true' }` block; the global `$default` now denies by default — see the Data Layer note above. **`messages` has since been tightened in cycle 0014** to a participant-scoped create + row-owner/owning-teacher update/delete rule, see the Student-chat note above; `questions` remains the deferred Batch-2 follow-up). The e2e suite is `e2e/auto-create-question.spec.ts` (a `?` message creates one linked Question + `QuestionCreated` event; a non-`?` message stays chat-only; skips loudly without admin env). **Schema push:** the three additive `question*` links require `npx instant-cli push schema` before the feature works against a schema-enforced live app.

**Teacher question queue + mark answered (cycle 0010):** the FIRST human consumer of the `Question` object — the teacher can now see open Questions and resolve them. `answerQuestion` / `buildQuestionAnswer` (`src/lib/sessions.ts`) are the **sole sanctioned resolution path**: `buildQuestionAnswer` is pure and totally validates input (present `questionId`/`sessionId`/actor `userId`, `actor.role: 'teacher'`, and the already-`answered` duplicate-resolution guard fed the LIVE status — mirroring `assertLegalTransition`) and trims an optional `answerSummary`, omitting it when blank, BEFORE producing any txn/envelope; `answerQuestion` routes the dual-write through `writeEvent('QuestionAnswered', …)` so the envelope (`actor.role: 'teacher'`, payload `{ questionId, sessionId, status: 'answered', addressedBy, answerSummary? }`) and the keyed `questions[id].update({ status, addressedBy, answerSummary? })` projection update commit in ONE transaction — no projection-only `questions` write exists in product code, and the rejection propagates to the caller (never swallowed). The projection update is a keyed upsert on the existing `questionId`, so a retry is naturally convergent; `answerQuestion` is otherwise NOT idempotent (each call appends a fresh envelope), with the already-`answered` guard + the component's per-Question `pendingId` latch suppressing a double-resolution. `applyEvent` (`src/lib/db.ts`) now folds `QuestionAnswered` (flips the row's `status` to `'answered'`, applies `answerSummary`/`addressedBy` when present, tolerant of an absent prior question — keyed by `questionId ?? event.id`) so the type never raises `UnknownEventTypeError` and `rebuildSessionProjection` stays whole; `SessionProjection.questions` gains optional `answerSummary?`/`addressedBy?` to carry them. The teacher queue is mounted INSIDE `SessionLifecycle` (`src/components/SessionLifecycle.tsx`) on `/dashboard/sessions/[id]` — a second `db.useQuery` over `questions` by `sessionId` pulling each Question's source-message text strictly via the `questionMessage` link (`questions: { $: { where: { sessionId } }, message: {} }`), filtered `status !== 'answered'` and sorted client-side by `createdAt` then `id`. **Teacher exclusion (SPEC §9.3) is preserved:** there is NO chat island and NO standalone `messages` query — the message is reached only as the Question's source, so a non-`?` chat message (which never becomes a Question) can never enter the queue. An empty queue shows an explicit empty-state element (never a blank region); a query error or a rejected answer write surfaces inline (`role="alert"`) + `console.error('[SessionLifecycle] …')`, leaving the Question in the queue to retry. The reused `questions` fields (`status`/`answerSummary`/`addressedBy`) already exist — **no schema push** — and `questions` was left open this cycle — **no `perms:push` this cycle** (cycle 0013 gave it an explicit open block; the global `$default` now denies by default). Fixed testids downstream cycles reuse: `teacher-question-queue` (container), `teacher-question-queue-empty` (empty state), `teacher-question-item` (per row, with `data-question-id`), `teacher-question-text`, `question-answer-summary` (optional input), `question-mark-answered` (button), `teacher-question-error` (inline alert). The e2e suite is `e2e/teacher-question-queue.spec.ts` (student `?` appears in the queue with no reload, non-`?` never does, answering with/without a summary removes it and writes a `QuestionAnswered` event + `answered` projection row; skips loudly without admin env).

**Teacher dashboard session list + open (cycle 0012):** the teacher now has a home base — a realtime, owner-scoped list of the sessions they own on `/dashboard`, each clickable into the existing facilitation view. The island is `SessionList` (`src/components/SessionList.tsx`), mounted as a nested `client:only="react"` island INSIDE `RouteGuard` on `/dashboard` **beside** `NewSession` (so it hydrates only when authenticated). Playwright drives the browser/e2e gate: run `npm run test:e2e:install` once to fetch Chromium, then `npm run test:e2e` — it starts its own dev server on port 4399 and verifies the `/dev/event-spine` dual-write spine, realtime cross-context sync, and the invalid-input failure path (`playwright.config.ts` sets `retries: 3` to absorb realtime-sync flake). Always also run `npm run astro check`. Name scenario files after the component or page they validate (e.g., `TodoApp.spec.ts`); unit specs live beside their module as `*.test.ts`, e2e specs in `e2e/`.

## Cycle walkthrough degradation sidecar
The walkthrough runner (`scripts/walkthrough-capture.mjs`) writes a **hook-owned** degradation sidecar `walkthrough-errors.json` (phase-aware: `walkthrough-<phase>-errors.json`) into `$CYCLE_ARTIFACT_DIR` on every run, carrying `{ degraded, reason, errors }`. This is independent of the **engine-owned** `walkthrough-artifacts.json` manifest, which records media files only. `degraded: true` means the per-cycle `walkthrough.mjs` was absent, unimportable, threw, or recorded no non-home captures, so the runner fell back to the home-page capture — the walkthrough is *not* real evidence of the cycle's functionality (the `reason` says why). The degradation decision is a pure, exported, total helper (`decideDegradation`) covered by `scripts/walkthrough-capture.test.mjs` (in the `npm run test` gate via the `scripts/**/*.test.mjs` include glob). The sidecar write is best-effort and never fails a cycle: `walkthrough_capture` always exits 0 and emits a loud `[blended-walkthrough] …` stderr diagnostic on any failure. The reflection step (`.cycle/prompts/reflection.md`) reads this sidecar and, for a `feature` cycle whose diff ships observable UI (`src/components/` or `src/pages/`), surfaces a `defer`/high sharp edge when the walkthrough is `degraded: true`.

## Environment & Secrets
Copy `.env.example` to `.env` and populate `PUBLIC_INSTANTDB_APP_ID` (the only required key for the app) before running the Todo demo, the event-spine harness, or any session feature. `PUBLIC_INSTANTDB_APP_ID` is also consumed by **`npm run schema:push`** and `npm run perms:push` (each fails loudly before any network call if it is missing); the live schema-verification e2e (`e2e/schema-push.spec.ts`) additionally requires `INSTANT_ADMIN_TOKEN`. `INSTANT_ADMIN_TOKEN` is an **e2e-only** key consumed by the Playwright auth suite to mint deterministic magic codes (`@instantdb/admin` `generateMagicCode` — no email is sent); it is Node-side only and never used by client/product code. When it is unset, `e2e/auth.spec.ts` skips loudly rather than passing falsely. `ADMIN_EMAILS` (cycle 0019) is a **server-only** comma/whitespace-separated allowlist of emails bootstrapped to the global `uber` admin level on sign-in — **no `PUBLIC_` prefix** (read via `process.env` in `/api/admin/bootstrap`, so it never reaches the client bundle); empty/unset ⇒ no admins are bootstrapped. Never commit populated `.env` files; instead, update `.env.example` when new variables are required and mention them in release notes.
