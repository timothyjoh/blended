# Repository Guidelines

## Project Structure & Module Organization
`src/` holds application code: page shells live in `src/pages`, shared UI in `src/components`, layout wrappers in `src/layouts`, domain logic and utilities in `src/lib`, and styling tokens in `src/styles`. Content collections (e.g., blog posts) live in `src/content`, while long-form references sit under `docs/`. Static assets ship from `public/`, and Tailwind configuration is centralized in `components.json`.

## Build, Test & Development Commands
Use `npm install` to sync dependencies. `npm run dev` starts the Astro dev server with hot reload. `npm run build` compiles the production site to `dist/`, and `npm run preview` serves that build for smoke-testing. `npm run astro check` runs Astro's type and content safety checks; call it before opening a pull request.

## Coding Style & Naming Conventions
Stick to modern TypeScript/JS without semicolons and two-space indentation, mirroring existing files. Favor `.astro` files for composition and `.tsx` React islands for interactive widgets. Co-locate feature assets (images, partials) with their component or page. Tailwind utility classes are preferred over ad-hoc CSS; keep custom styles in `src/styles` when utilities fall short.

## Data Layer (Blended event spine)
`src/lib/db.ts` is the **single** place that initializes the InstantDB client and defines the Blended `i.schema` (entities `users`, `sessions`, `sessionResources`, `participants`, `sessionEvents`, `messages`, `questions`, `endorsements`). Product code imports the `db` client and schema-derived types from this module — do not call `init()` or redeclare schema elsewhere. It throws at module init if `PUBLIC_INSTANTDB_APP_ID` is missing rather than building a broken client.

**All product mutations MUST route through `writeEvent(type, meta, projectionTxns)`** (ADR-0001, ADR-0003). It appends a SPEC §7.2 `sessionEvents` envelope **and** applies the caller's projection update(s) inside one `db.transact()`, so the event log and projections stay consistent and every interaction is replayable. No product code path may write a Blended projection row (`db.tx.<entity>[…].update/delete`) outside the helper — a projection-only write is a bug (the legacy `todos` demo is exempt). `applyEvent` / `rebuildSessionProjection` in the same module fold an ordered event list back into a projection (SPEC §17.1) and surface unknown event types loudly. InstantDB entity ids must be UUIDs (use `id()` re-exported from `@/lib/db`).

The dev-only scratch harness `/dev/event-spine` (`src/components/EventSpineHarness.tsx`) exercises the dual-write path for two event types and renders the live event/projection rows; it is disabled in production builds. Under the permission rules below it writes as the **signed-in** user (sign in at `/login` first), so its session/participant rows are owned by `user.id`. If writes are rejected with a schema error, push the schema to the Instant app once with `npx instant-cli push schema`.

### Permission rules / data-layer authorization
`src/lib/perms.ts` is the **single source** of the InstantDB permission rules (cycle 0003); the root `instant.perms.ts` is only a CLI adapter that re-exports it (what `instant-cli push perms` loads). The rules enforce two SPEC invariants at the data layer so they hold even against a hand-crafted client, not just the UI:

- **`users` is own-row-only** (`view/create/update = auth.id == data.id`, `delete = false`). The canonical **private email lives ONLY here** — no client can read another user's row, so no email leaks. The `users` row id IS the auth id, so first-sign-in creation stays permitted.
- **`sessions` and `sessionResources` are owner-only writes** (`auth.id == data.teacherId`) with **open reads** (students must follow the lesson). This protects session lifecycle and the `activeResourceId` projection (and the later `currentUrl` field, which inherits the same policy). `sessionResources` carries a denormalized `teacherId` (mirrors `sessions.teacherId`) so ownership is checkable without link traversal — future `writeEvent` resource creators MUST populate it.
- **`sessionEvents` is append-only by any authenticated participant** (`create = auth.id != null`, no client `update`/`delete`) — keeps `writeEvent()` legal, including first-sign-in identity writes.
- **`participants` carry NO email** — InstantDB view rules are row-level, not column-level, so email privacy is structural: the field is removed from the entity, not masked by a rule. ⚠️ `participants` `update`/`delete` are currently **fail-open** (`auth.id != null`) — any signed-in user could mutate or delete another's participant row. No participant rows are written yet; the join-via-link cycle MUST restrict these to the row owner (`auth.id == data.userId`) plus the owning teacher/admin before creating them.
- **System/admin** actions run through `@instantdb/admin`, which **bypasses** these rules; the future client-side admin slot is reserved by the `isAdmin` bind (`false` today, ADR-0003 `User.adminLevel`). A permissive `$default` keeps `todos` and the out-of-scope Batch-2 namespaces at today's behavior.

Push the rules with **`npm run perms:push`** (a fail-loud wrapper around `npx instant-cli push perms` — exits non-zero with a clear message on missing app id or CLI/auth/network failure; idempotent, safe to re-run), after `npx instant-cli push schema` so the schema delta (`sessionResources.teacherId`, removed `participants.email`) is live. The rules' semantics are pinned by a structural unit test (`src/lib/perms.test.ts`) and proven end-to-end against the live app by `e2e/permissions.spec.ts` (skips loudly without `INSTANT_ADMIN_TOKEN`).

**Auth** is reached through one shared hook: `useAuth` (`src/lib/useAuth.ts`) wraps `db.useAuth()` + the magic-code auth namespace and exposes `{ user, isLoading, error, username, sendCode, verifyCode, signOut }`. Product code MUST NOT call `db.useAuth()` directly outside this hook — all auth state flows through `useAuth` so later cycles consume identity from one place. The signed-in view shows the derived `username` (email local-part), never the raw email (SPEC §40). First-sign-in `users`-row creation goes through `writeEvent()` under the reserved `IDENTITY_SCOPE` sentinel sessionId (`src/lib/auth.ts`) with actor role `'unknown'` and a `UserSignedIn` event — guarded by `shouldCreateUserRow` so it is idempotent across reloads and repeat sign-ins. `UserSignedIn` is intentionally OUTSIDE the session fold: `applyEvent` throws `UnknownEventTypeError` on it by design (identity events belong to no real session). The product sign-in surface is `/login` (`src/pages/login.astro` → `src/components/AuthGate.tsx`).

**Route guarding** (cycle 0004): `RouteGuard` (`src/components/RouteGuard.tsx`) is the SINGLE client-side gate for protected islands — it consumes `useAuth` (never `db.useAuth()`) and resolves four states: `route-guard-loading` (auth unresolved — never redirects, avoiding a flash-redirect), an unauthenticated bounce to `/login?next=<encoded dest>` via `window.location.replace`, `route-guard-denied` (auth error or failed ownership check — logged via `console.error`, never collapsed to "authenticated"), and the rendered children. Guarding is client-side by design because auth state is client-held (SSR pages render a shell that hydrates and decides); there is no server/middleware protection. `safeNextPath` (`src/lib/routing.ts`) is the ONLY sanctioned way to resolve a post-login destination — it honors a `next` only when it is a same-origin absolute path, otherwise falling back to `/dashboard`, so a crafted `?next=` cannot drive an open redirect; `AuthGate` calls it after sign-in (and routes an already-signed-in `/login` load to `/dashboard`). Ownership-scoped routes use `SessionRouteGuard` (`src/components/SessionRouteGuard.tsx`), which runs the `sessions` `db.useQuery` and folds the result through the pure `authorizeOwnership` helper (`session.teacherId === user.id`) into a precomputed `authorize` decision passed to `RouteGuard` (hooks can't run inside a predicate closure). `/dashboard` and `/dashboard/sessions/[id]` are placeholder shells only (real screens are later cycles). Fixed testids for downstream cycles: `route-guard-loading`, `route-guard-denied`, `dashboard-root`, `session-root`.

**Session creation** (cycle 0005): sessions are created via `createSession` (`src/lib/sessions.ts`), the only sanctioned create path — it routes the dual-write through `writeEvent('SessionCreated', …)`, so the `SessionCreated` envelope and the `draft` `sessions` projection row commit in one transaction (a rejected create leaves no partial state). The module keeps the auth.ts-style pure-core split: `generateJoinCode` is the sanctioned **unguessable** join-code source (length `JOIN_CODE_LENGTH` = 10 over the unambiguous charset `JOIN_CODE_ALPHABET`, crypto-backed with an injectable RNG for deterministic tests), and `buildSessionCreate` totally validates input (rejects blank/whitespace title and missing `teacherId` BEFORE producing any txn) and builds the record + envelope meta (`actor.role: 'teacher'`, `sessionId === payload.id`). `createSession` is NOT idempotent by design (each call mints a fresh `sessionId`/`joinCode`). The dashboard control is `NewSession` (`src/components/NewSession.tsx`), a nested island inside `RouteGuard` that reads identity via `useAuth` — **creating a session is what makes a user its teacher** (a session-scoped role, not an account type; any signed-in user may create one). Fixed testids downstream cycles reuse: `new-session-open`, `new-session-title`, `new-session-submit`, `new-session-error`, `created-session`, `created-session-title`, `created-session-status`, `created-session-joincode`. The e2e seam adds a Node-side admin read helper `queryAdmin` (`e2e/support/auth.ts`) for observability assertions.

## Testing Guidelines
Vitest covers pure logic modules: `npm run test` (CI mode), `npm run test:watch`, and `npm run test:coverage`. Playwright drives the browser/e2e gate: run `npm run test:e2e:install` once to fetch Chromium, then `npm run test:e2e` — it starts its own dev server on port 4399 and verifies the `/dev/event-spine` dual-write spine, realtime cross-context sync, and the invalid-input failure path (`playwright.config.ts` sets `retries: 3` to absorb realtime-sync flake). Always also run `npm run astro check`. Name scenario files after the component or page they validate (e.g., `TodoApp.spec.ts`); unit specs live beside their module as `*.test.ts`, e2e specs in `e2e/`.

## Commit & Pull Request Guidelines
Follow the existing short, imperative commit style (`bbc7a3c better aside styles, with mobile`). Group related changes into a single commit and reference issue IDs when available. Pull requests should summarize the user-facing impact, list verification steps (`npm run build`, route screenshots), and note any config or environment changes such as new `.env` keys. Request review from maintainers familiar with the touched area (UI, data, content).

## Environment & Secrets
Copy `.env.example` to `.env` and populate `PUBLIC_INSTANTDB_APP_ID` (the only required key for the app) before running the Todo demo, the event-spine harness, or any session feature. `INSTANT_ADMIN_TOKEN` is an **e2e-only** key consumed by the Playwright auth suite to mint deterministic magic codes (`@instantdb/admin` `generateMagicCode` — no email is sent); it is Node-side only and never used by client/product code. When it is unset, `e2e/auth.spec.ts` skips loudly rather than passing falsely. Never commit populated `.env` files; instead, update `.env.example` when new variables are required and mention them in release notes.
