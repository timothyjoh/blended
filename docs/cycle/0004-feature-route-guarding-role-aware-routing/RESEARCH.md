# Research: Cycle 0004

## Cycle Context
SPEC.md (`docs/cycle/0004-feature-route-guarding-role-aware-routing/SPEC.md`) asks for a single reusable client-side route guard for the InstantDB-authenticated SPA islands, plus thin protected placeholder destinations to prove the gate end-to-end. Concretely: a `RouteGuard` React island (`src/components/RouteGuard.tsx`) that reads identity through the shared `useAuth` hook and resolves to one of four states — loading, unauthenticated (redirect to `/login?next=<encoded path+search>`), authorized (render children), and graceful denial — with an optional `authorize` predicate for ownership-scoped routes; a pure `safeNextPath` helper (`src/lib/routing.ts`) that validates the `next` param as a same-origin absolute path (open-redirect-safe); a post-sign-in redirect added to `AuthGate` that returns the user to a valid `next` or falls back to `/dashboard` (and routes an already-signed-in `/login` load to `/dashboard`); and minimal guarded pages `/dashboard` (auth-only) and `/dashboard/sessions/[id]` (ownership-scoped via `sessions.teacherId == user.id`). Out of scope: real dashboard/session/join screen contents, admin gating, server/middleware protection, and join-as-participant logic.

### Existing Patterns to Follow
- **Pure-logic module + co-located unit test**: db-free helpers live in `src/lib/*.ts` and are tested in `src/lib/*.test.ts` with Vitest (`describe`/`it`/`expect`, `it.each` for table-driven failure cases). `safeNextPath` should mirror `src/lib/auth.ts` + `src/lib/auth.test.ts`. — `src/lib/auth.ts:24-29`, `src/lib/auth.test.ts:20-43`
- **React island pattern**: interactive widgets are `.tsx` default-export components consuming `useAuth`; mounted from `.astro` pages with `client:only="react"` (auth-dependent islands cannot SSR because auth state is client-held). — `src/components/AuthGate.tsx:17`, `src/pages/login.astro:11`, `src/components/PermsProbe.tsx:23`
- **Single auth seam rule**: product code reads identity ONLY through `useAuth`, never `db.useAuth()` directly (`AGENTS.md` "Auth" note). `useAuth` already exposes `user`, `isLoading`, `error`. — `src/lib/useAuth.ts:32-33`, `AGENTS.md` Data Layer section
- **Page shell convention**: protected pages reuse `Layout.astro` (accepts a `title` prop, renders a `<slot/>` inside `<main>`) with Tailwind utility classes; shadcn primitives are imported from `@/components/ui/*` (e.g. `button`, `input`). `@/*` resolves to `./src/*` (tsconfig paths). — `src/layouts/Layout.astro:15,45-47`, `src/components/AuthGate.tsx:4-5`, `tsconfig.json:9-10`
- **Prod-gating of non-product routes**: dev harness pages branch on `import.meta.env.PROD` and render a `data-testid="dev-disabled"` fallback instead of the island. (Placeholder protected pages in this cycle are product routes, not dev-gated — but this is the existing gating idiom.) — `src/pages/dev/perms-probe.astro:8,14-21`
- **Query-by-id projection read**: islands read a session via `db.useQuery({ sessions: { $: { where: { id } } } })` and pull `data.sessions[0]`; a `null` query is passed when there is no id so InstantDB skips it. This is the pattern the ownership-scoped guard's `sessions` read should follow. — `src/components/PermsProbe.tsx:30-33`, `src/lib/useAuth.ts:40`
- **Failure handling (current convention)**: errors are surfaced to a rendered state AND logged with `console.error('[Component]', err)` — never swallowed. `AuthGate` writes the message to an inline `role="alert"` element; `PermsProbe` writes `'error:' + message` to a testid; `useAuth` logs row-creation failure and lets auth state stand. The SPEC requires the guard to follow this: ownership query error / no row → render `route-guard-denied` and `console.error`; non-null `useAuth().error` → log + reflect in rendered state. — `src/components/AuthGate.tsx:25-29`, `src/components/PermsProbe.tsx:35-39`, `src/lib/useAuth.ts:77-82`
- **Observability**: the project's structured event log is `.cycle/log.jsonl` (cycle engine, not app runtime). At the application/runtime level there is no metrics/structured-logging layer — the only convention is `console.error` with a bracketed component tag. — `src/components/AuthGate.tsx:28`, `src/lib/useAuth.ts:81`
- **Idempotency / guard logic**: the established pattern for retry-safety is a pure predicate fed by render-derived state plus a `useRef` in-flight latch (`shouldCreateUserRow` + `inFlight` ref). The guard's redirect should likewise avoid acting before auth resolves (loading state must NOT redirect, per SPEC, to prevent flash-redirect). — `src/lib/auth.ts:47-55`, `src/lib/useAuth.ts:35,45-86`
- **Loading-before-decide**: `AuthGate` returns a stable loading view while `isLoading` is true before branching on `user`. The guard must do the same and render `data-testid="route-guard-loading"`. — `src/components/AuthGate.tsx:98-104`

## Open Questions
- **Redirect mechanism**: the codebase has no existing client-side navigation/redirect helper (no router library; pages are Astro routes). Whether the guard and `AuthGate` should redirect via `window.location.assign`/`.replace` vs. another mechanism, and how to read the current `pathname+search` at redirect time, is unspecified by existing code — to be resolved in planning. (The only precedent for reading the URL is `new URLSearchParams(window.location.search)` in `PermsProbe.tsx:14-17`.)
- **Reading the `next` param in `AuthGate`**: `AuthGate` currently takes no props and does not read the URL; how `next` reaches the post-sign-in redirect (prop passed from `login.astro` vs. read from `window.location` inside the island) is undecided.
- **`authorize` predicate signature & async timing**: the SPEC describes an optional `authorize` predicate for ownership-scoped routes backed by a `sessions` query, but how the guard threads an async/loading query result through the four-state machine (loading vs. denied vs. authorized while the ownership query resolves) is an implementation detail not yet modeled in code.
- **Passing the session `id` into the guarded `[id]` page's island**: Astro dynamic route params are server-side; the hydrated guard island needs the id client-side (via prop or `window.location` parse) — the established island-prop vs. URL-parse choice (cf. `PermsProbe`'s query-param read) needs to be fixed in planning.
- **`route-guard-*` testid set**: SPEC names `route-guard-loading`, `route-guard-denied`, and references `session-root`/`session-shell` for placeholders; the exact testids for the authorized/dashboard shells (e.g. `dashboard-root`) are not yet fixed and should be settled so downstream cycles can reuse them.
