# Research: Cycle 0011

## Cycle Context
SPEC.md (`docs/cycle/0011-feature-make-cycle-walkthrough-degradation-loud/SPEC.md`) requires persisting the walkthrough-degradation signal that the runner already computes but currently discards. The walkthrough runner (`scripts/walkthrough-capture.mjs`) falls back to a homepage-only capture whenever the per-cycle `walkthrough.mjs` scenario is absent, unimportable, or throws, but that degradation is never written to disk — it is byte-for-byte indistinguishable from an intentional walkthrough. This cycle adds: (1) an explicit `{ degraded, reason }` result computed by a new **pure, exported, total helper**, serialized to a hook-owned `walkthrough-errors.json` sidecar (phase-aware naming mirroring the engine's `walkthrough-<phase>-artifacts.json`); (2) a Vitest unit test of that pure helper + serialization covering both real-scenario (`degraded: false`) and fallback (`degraded: true` + reason) paths; (3) a `.cycle/prompts/reflection.md` rule that reads the sidecar and surfaces a `defer`/high sharp edge when a `feature` cycle shipped observable UI but the walkthrough is degraded. Quickfix `walkthrough_before`/`walkthrough_after` wiring is explicitly out of scope (deferred to a sibling cycle; only the sidecar naming is made phase-aware to enable it).

### Existing Patterns to Follow
- **Pure-core split** (the convention the new helper must mirror): impure I/O is kept thin; decision logic is extracted into an exported, deterministic, dependency-free function that unit-tests without a server/network. Canonical examples: `buildSessionCreate` / `buildSessionStart` / `buildSessionEnd` in `src/lib/sessions.ts:76`, `:200`, and the surrounding header comment `src/lib/sessions.ts:5-8`, `:138-143`. The pure builder "totally validates input … BEFORE producing any txn" and never throws on bad input — same totality the SPEC requires of the degradation helper.
- **Failure handling (existing, to preserve verbatim)**: every degraded branch pushes a human-readable string onto `errors[]` and emits a loud one-line stderr diagnostic via `logDiag` (`[blended-walkthrough] …`) — `scripts/walkthrough-capture.mjs:43-45`, used at `:119-121`, `:141-143`, `:167`, `:195`, `:204`, `:229`, `:240-241`, `:245`, `:248-249`, `:270`, `:272`. Nothing is swallowed silently. The runner NEVER throws out of `captureWalkthrough` (every stage wrapped in try/catch returning early with the accumulated `{ media, chapters, errors }`) and `main()` unconditionally `process.exit(0)` — `scripts/walkthrough-capture.mjs:262-280`. The new sidecar write must be best-effort: on failure log a `[blended-walkthrough] …` diagnostic and still exit 0 (SPEC Requirements + Failure behavior).
- **Observability conventions**: hook-side = stderr `[blended-walkthrough] …` lines only (no structured events from the `.mjs`). Engine-side structured events go to `.cycle/log.jsonl` (e.g. `step.walkthrough_capture_failed` at `.cycle/bin/cycle.js:10402-10407`, `step.end` with optional `walkthrough_artifacts` at `:10414-10420`). The reflection prompt observes engine events via `tail -n 200 .cycle/log.jsonl` — `.cycle/prompts/reflection.md:26`.
- **Idempotency / retry-safety**: the runner is naturally idempotent — each run re-creates `mediaDir` with `mkdir({recursive:true})` (`scripts/walkthrough-capture.mjs:193`, `:113`, `:215`) and overwrites screenshots/video by fixed name; there is no dedup key or lock in the hook. The sidecar write should likewise overwrite by fixed (phase-aware) name. A repo-level `.cycle/engine.lock` exists (untracked, in git status) as the engine's run guard — not touched by the hook.
- **Phase-aware naming convention to mirror**: engine uses `walkthrough-${phase}-artifacts.json` / `walkthrough-artifacts.json` — `.cycle/bin/cycle.js:9965-9967`. SPEC asks the sidecar to mirror this: `walkthrough-errors.json` (no phase) / `walkthrough-${phase}-errors.json` (phase set via `CYCLE_WALKTHROUGH_PHASE`).
- **Reflection sharp-edge routing**: bucket/priority bright-line table — a `defer` entry **requires** a `priority` field (`critical|high|medium|low`) — `.cycle/prompts/reflection.md:84-101`. The new rule must emit `bucket: "defer"`, `priority: "high"`. Observable-UI heuristic the SPEC names: diff "touches `src/components/` or `src/pages/`".

## Open Questions
- **Vitest include glob vs. test location**: `vitest.config.ts` `include: ['src/**/*.test.ts']` will not match a test placed beside the `.mjs` runner under `scripts/`, yet the SPEC says co-locate "beside the runner under `scripts/`." The planner must reconcile this — either extend the `include` glob (and possibly coverage `include`) to cover `scripts/`, or relocate/export the pure helper so a `src/**/*.test.ts` file can import it. (The SPEC's automated-gate requirement is that `npm run test` runs the new test.)
- **Where the pure helper lives & what it imports**: the runner must stay `playwright` + node-built-ins-only (no project `.ts` imports). If the helper is exported from the `.mjs` and the test is a `.ts` under `src/`, the test would import a `.mjs` from `scripts/` — the planner should confirm Vitest resolves that cleanly under the `node` environment.
- **Degradation signal threading**: today `runScenarioOrFallback` returns `void` and the only on-disk/in-memory markers of a fallback are the `errors[]` reason strings and the presence of the `00-home` chapter. The planner must decide the exact input shape passed to the pure helper (e.g. a structured `{ ranScenario, fellBack, reason, chapters, errors }`) so the decision is total and unambiguous — note a real scenario may legitimately push non-fatal `errors` (e.g. a single failed `capture`) without being degraded.
- **How reflection determines the workflow is `feature`**: no `CYCLE_WORKFLOW` env var is exported to the prompt; the workflow is encoded in the artifact-dir name. The prompt rule must specify how the agent derives "this is a `feature` cycle" (e.g. parse the cwd dir name `<id>-<workflow>-<slug>`).
- **Sidecar phase-aware naming exactness**: confirm the precise filename for the phased case (`walkthrough-before-errors.json` / `walkthrough-after-errors.json`) to stay parallel with the engine's `walkthrough-<phase>-artifacts.json`, even though phased steps are out of scope for behavior this cycle.
