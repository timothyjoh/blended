# Research: Cycle 0010

## Cycle Context
SPEC.md (`docs/cycle/0010-feature-teacher-question-queue-mark-answered/SPEC.md`) asks for the teacher-facing consumer of the `Question` object created in cycle 0009. Two deliverables: (1) a new sanctioned answer path in `src/lib/sessions.ts` — a pure `buildQuestionAnswer` + thin `answerQuestion` wrapper that routes a dual-write through a new `writeEvent('QuestionAnswered', …)`, updating the `questions` projection row to `status: 'answered'` (with optional `answerSummary` and `addressedBy: <teacher userId>`), plus a matching `QuestionAnswered` fold in `applyEvent` (`src/lib/db.ts`); and (2) a realtime, session-scoped open-Question queue rendered inside the existing `SessionLifecycle` island on `/dashboard/sessions/[id]`, showing only Questions whose `status !== 'answered'`, never raw chat messages, with a per-Question mark-answered control (optional summary input). Reuses the existing `questions` schema fields (`status`/`answerSummary`/`addressedBy` already defined) — **no schema or permission push this cycle**. Vitest covers the builder + fold; a Playwright e2e covers the realtime ask→see→answer loop.

### Existing Patterns to Follow
- **Pure-core / thin-wrapper split**: every mutation has a pure `build*` that totally validates and returns `{ record/update, meta }` BEFORE any write, plus an async wrapper that calls `writeEvent`. Examples: `buildSessionCreate`/`createSession` (`src/lib/sessions.ts:76-135`), `buildSessionStart`/`startSession` (`:200-271`), `buildParticipantJoin`/`joinSession` (`:342-427`), `buildChatMessage`/`submitChatMessage` (`:481-658`), `buildQuestion` (`:568-592`). `buildQuestionAnswer`/`answerQuestion` must mirror this shape.
- **Validate-before-act / throw on bad input**: builders throw synchronously on missing required input, writing nothing — e.g. `buildSessionStart` (`src/lib/sessions.ts:200-217`) checks present id, owner identity, legal transition; `buildQuestion` (`:568-592`) checks present `sessionId`/`participantId`/`userId`. SPEC requires `buildQuestionAnswer` to reject missing `questionId`/`sessionId`/actor `userId`, require `actor.role: 'teacher'`, and trim+omit a blank `answerSummary`.
- **Injectable `deps` for unit testing**: wrappers accept `{ write?, buildTxn? }` so tests stub `writeEvent` and the txn builder. See `CreateSessionDeps` (`src/lib/sessions.ts:101-104`), `TransitionDeps` (`:243-249`), `SubmitChatMessageDeps` (`:601-605`). Default txn builders (`defaultBuildTxn` etc.) construct `db.tx.<entity>[id].update(...).link(...)`.
- **Default projection txn for questions (cycle 0009 reference)**: `defaultQuestionTxn` (`src/lib/sessions.ts:594-599`) does `db.tx.questions[r.id].update({ sessionId, status, createdAt }).link({ message, participant, session })` — scalar columns only, links carry identity. The answer txn will `update` `status`/`answerSummary`/`addressedBy` on the existing row id.
- **`writeEvent` dual-write contract**: `src/lib/db.ts:441-479` — requires `type`, `meta.sessionId`, `meta.actor` with a valid `role` (from `ACTOR_ROLES`, `src/lib/db.ts:29`), and a non-empty `projectionTxns` array; appends one `sessionEvents` envelope + the projection txns in one `db.transact()`. Validates synchronously and throws before any transaction.
- **`applyEvent` fold pattern**: `src/lib/db.ts:264-389` — a `switch (event.type)`, each case defensively reads `event.payload`, tolerates absent prior state / partial payload with typed defaults, never mutates input (spreads a new projection), and re-folding reproduces the same entry. The `default` throws `UnknownEventTypeError` (`src/lib/db.ts:236-241, 382-387`). `QuestionCreated` fold is the closest template (`src/lib/db.ts:349-381`). A new `QuestionAnswered` case must flip the existing question's `status` to `answered` and apply `answerSummary`/`addressedBy`.
- **`SessionProjection.questions` shape (note current fields)**: `src/lib/db.ts:222-232` — currently `{ id, messageId, participantId, sessionId, status, createdAt }`. It does **not** yet carry `answerSummary` or `addressedBy`; a `QuestionAnswered` fold that records those needs the projection type extended.
- **Realtime query + client-side sort convention**: components read via `db.useQuery` filtered by `sessionId` and sort client-side by `createdAt` then `id` (no server order index). See `StudentChat` messages query+sort (`src/components/StudentChat.tsx:53-60`). The teacher queue must query `questions` by `sessionId`, filter `status !== 'answered'`, sort by `createdAt` then `id`.
- **Identity via `useAuth` (never `db.useAuth()`)**: `src/components/SessionLifecycle.tsx:24`, `src/components/StudentChat.tsx:31`. AGENTS.md:30 mandates all auth state flows through `useAuth`.
- **Failure handling (the convention to match)**: components surface failures inline via a `role="alert"` element AND `console.error('[<Component>] …')`, never swallowed. `SessionLifecycle.surface` (`src/components/SessionLifecycle.tsx:35-39`) sets an error string + logs; query errors are logged at `:31`; the alert `<p data-testid="session-lifecycle-error" role="alert">` at `:68-76`. `StudentChat` mirrors this (`:71-80`, `:160-164`). The dual-write rejection propagates to the caller (never swallowed) — `writeEvent` returns the `db.transact()` promise (`src/lib/db.ts:478`).
- **State-unchanged-on-failure**: lifecycle transitions leave displayed status untouched on rejection because the UI is driven by the live query (`src/components/SessionLifecycle.tsx:59-66`). The answered Question must stay in the queue on a failed write.
- **Stale-tab / duplicate guard via current-status check**: `assertLegalTransition` fed the LIVE status rejects re-issues (`src/lib/sessions.ts:165-173, 200-217`). SPEC requires answering an already-`answered` Question to be rejected/no-op — guard on the current `status` (analogous pattern).
- **Idempotency notes**: `writeEvent` is NOT idempotent by design — each call appends a fresh event (`src/lib/db.ts:436-438`). Cycle-0009 Question rows use a deterministic derived id (`deriveQuestionId`) for keyed-upsert idempotency, but the answer write updates an existing known `questionId`, so the projection update is naturally a keyed upsert on that row.
- **Observability / structured events**: every interaction is a `sessionEvents` envelope (SPEC §7.2) appended by `writeEvent` (`src/lib/db.ts:465-478`) with `type`, `actorRole`, `occurredAt`/`receivedAt`, `payload`. The cycle adds a `QuestionAnswered` envelope type. Component-level logging uses the `[ComponentName] …` `console.error` prefix convention.
- **Teacher exclusion (must preserve)**: `SessionLifecycle` deliberately mounts NO chat island (SPEC §9.3; AGENTS.md:40, `src/components/StudentChat.tsx:26-28`). The queue renders Questions only — never rows from the `messages` entity.

## Open Questions
- The `SessionProjection.questions` map (`src/lib/db.ts:222-232`) currently has no `answerSummary`/`addressedBy` fields. The planner must decide whether the `QuestionAnswered` fold extends that type to record those fields or only flips `status` — SPEC §AC requires the fold to "apply `answerSummary`/`addressedBy`," implying the projection type needs those keys added.
- SPEC requires guarding against answering an already-`answered` Question ("rejected/no-ops rather than appending a duplicate"). The current Question's `status` is read from the live `db.useQuery` in the component, not passed into the pure builder; the plan must decide where the guard lives (pure builder fed current status, mirroring `assertLegalTransition`, vs. component-level pre-check) — to be resolved at plan time.
- Exact new fixed testids for the queue (queue container, per-Question item, mark-answered control, summary input, empty-state element) are not yet named; SPEC says to document them in AGENTS.md but leaves the specific strings to the plan/build.
