# Research: Cycle 0013

## Cycle Context
This cycle closes the fail-open authorization hole described in source issue `refl-0003`. The InstantDB permission object in `src/lib/perms.ts` currently ends with a permissive global catch-all `$default: { allow: { $default: 'true' } }` (`src/lib/perms.ts:26`). Four schema entities — `todos`, `messages`, `questions`, `endorsements` — carry no explicit rule block and therefore inherit this catch-all, leaving them fully world-readable and world-writable, and any *new* schema entity is silently world-open by default. SPEC requires flipping `$default` to deny-by-default (`'false'`), adding explicit, behavior-preserving `allow` blocks for the four currently-default-governed entities so no functional regression occurs, updating the structural guard test (`src/lib/perms.test.ts`) and the `perms.ts` header comment to assert deny-by-default and per-entity explicit rules, extending `e2e/permissions.spec.ts` with an unauthorized-write rejection case, and updating `AGENTS.md`/`README.md` docs. The participant owner-scoped write rule the issue is titled for already shipped (cycle 0007); this cycle only regression-verifies it. This is a data-layer authorization change only — no UI change.

### Existing Patterns to Follow
- **Per-entity rule block shape**: each entity is `{ bind?: string[], allow: { view, create, update, delete } }` with CEL-style string expressions. `view` is `'true'` where reads must stay open (`sessions`/`sessionResources`/`sessionEvents`/`participants`); writes use bound predicates. — `src/lib/perms.ts:28-114`.
- **`bind` for forgery-proof ownership**: ownership is checked against the LINKED parent session via `data.ref('session.teacherId')`, never a client-supplied denormalized field — `sessionResources` (`src/lib/perms.ts:70`), `participants` (`src/lib/perms.ts:105`). The `isAdmin` slot is reserved as literal `'false'` today (`perms.ts:49,70,107`).
- **Append-only / immutable pattern**: `sessionEvents` uses `create: 'auth.id != null'`, `update: 'false'`, `delete: 'false'` — the closest existing template for "authenticated may create, no one mutates" — `src/lib/perms.ts:83-90`.
- **Inferred-literal contract (no type annotation)**: the `rules` object intentionally omits the `InstantRules<…>` annotation so the structural guard gets precise, non-optional property access; `astro check` confirms well-formedness — documented at `src/lib/perms.ts:14-19`. SPEC requires this stays a plain inferred literal.
- **Structural-guard assertion style**: each test reads the exact expression string and asserts both positive intent and negative regressions (`.not.toBe('true')`, `.not.toBe('auth.id != null')`, `.toContain(...)`) — `src/lib/perms.test.ts:11-73`. The participants regression guards (`src/lib/perms.test.ts:55-73`) and the root-adapter identity test (`:79-83`) are the SPEC-named tests that must continue to pass unchanged.
- **Header-comment convention**: `perms.ts` carries a multi-line rationale block explaining each invariant and why the type annotation is omitted — `src/lib/perms.ts:1-25`; per-block inline comments precede each entity (`perms.ts:22-25, 28-33, 42-48, 58-69, 79-82, 92-101`). SPEC requires replacing the catch-all note (`:22-25`) with deny-by-default rationale and an explicit list of intentionally-open entities.
- **Failure handling (live rules)**: an unauthorized client write causes InstantDB to reject the transaction — the `db.transact(...)` promise rejects and the probe surfaces `'error:' + message` to a testid plus `console.error('[PermsProbe]', err)`, never swallowed — `src/components/PermsProbe.tsx:35-39, 56-65`. The e2e asserts the rejection AND that the stored value is unchanged — `e2e/permissions.spec.ts:82-88`.
- **Failure handling (push runner)**: every failure path (missing app id, un-spawnable CLI, non-zero CLI exit) exits non-zero with a clear message before/around the network call so the live app is never silently left unprotected — `scripts/push-perms.mjs`. Idempotent: re-pushing identical declarative rules is a no-op.
- **Observability**: the cycle event log is `.cycle/log.jsonl` (`cycle.start` records `cycle_id`/`workflow`/`title`/`issue_id`). Product-side errors follow the `console.error('[Component] …')` convention (`PermsProbe.tsx:38`). The permission rules themselves have no runtime logging — enforcement is by InstantDB rejecting transactions; the structural unit test is the in-repo guard and `e2e/permissions.spec.ts` is the live proof.
- **Idempotency / retry-safety**: rules are declarative — `instant-cli push perms` is a no-op when identical, safe to re-run (`scripts/push-perms.mjs` header). The structural guard test is the authority if a push cannot reach the live app: it must fail (not pass silently) if `$default` is loosened or an entity lacks an explicit rule.

## Open Questions
- **`todos` entity is not in the schema.** SPEC and the existing `perms.ts:22` comment treat `todos` as a currently-default-governed entity that must "stay open," but `i.schema({ entities: … })` in `src/lib/db.ts:38-134` defines no `todos` entity (only the eight MVP entities). The planner must resolve whether `todos` is an InstantDB built-in/implicit namespace requiring an explicit `todos` rule block, or whether it should be omitted (and only `messages`/`questions`/`endorsements` given explicit blocks). This determines exactly which explicit `allow` blocks are added.
- **Exact "behavior-preserving" expressions for `messages`/`questions`/`endorsements`.** SPEC mandates preserving *today's* runtime behavior (currently fully open: `view/create/update/delete` all effectively `'true'` via the catch-all) and explicitly defers the real read-visibility/write-authorization policy to Batch-2. The planner must decide the precise strings (e.g. all-`'true'`, or `auth.id != null` for writes) that keep the four product flows green while making openness intentional — SPEC says "preserve today's open behavior," so the conservative reading is all-`'true'`, but this should be confirmed against what `submitChatMessage` / question writes / endorsement writes require (signed-in vs. unauthenticated).
- **Whether the new e2e failure-path probes against a default-governed entity require a new `PermsProbe` handler + testid** (none exists today) and whether such a write, under all-`'true'` preservation, would actually be *rejected* — if the four entities stay open, the rejection case may need to target a genuinely undeclared/unknown entity instead of `messages`/`questions`/`endorsements`. The planner must reconcile the SPEC acceptance criterion (unauthorized write to a "default-governed OR undeclared entity" is rejected) with the requirement that the four named entities keep working.
- **Whether `perms:push` is run this cycle.** Prior cycles (0008–0012) explicitly did NOT push; SPEC's failure-behavior section treats the source-of-truth object + structural test as the authority and notes the live push may be deferred. The planner should confirm push expectation (the e2e live verification requires the rules to be pushed against the app).
