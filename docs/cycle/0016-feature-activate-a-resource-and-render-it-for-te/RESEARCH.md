# Research: Cycle 0016

## Cycle Context
SPEC.md asks for the activation vertical slice that connects the queued-resource list (cycle 0015) to the student audience (cycle 0007). It requires three coordinated additions: (1) a sanctioned teacher-only write path — `activateResource`/`buildResourceActivate` in `src/lib/sessions.ts` — that dual-writes a `ResourceActivated` event and sets `sessions[id].activeResourceId` + a new derived `currentUrl` projection field in one transaction; (2) a teacher **Activate** control on each queued-resource row in `SessionLifecycle`, with the active resource visibly indicated; and (3) a single shared `ResourcePane` component rendering the active resource in a controlled (sandboxed) iframe, mounted in both the teacher facilitation view (`SessionLifecycle`) and the student view (`StudentSession`), updating live via existing `db.useQuery` subscriptions. It also requires an additive `sessions.currentUrl` schema field, an `applyEvent('ResourceActivated', …)` fold, and `SessionProjection.session` gaining `activeResourceId?`/`currentUrl?`. No permission-rule change — the writes inherit the existing `sessions` owner-only rule. No product code path writing `activateResource`/`buildResourceActivate`/`ResourcePane`/`currentUrl`/`<iframe>`/`ResourceActivated` exists today outside mockups and prose (`src/components/mockups/TeacherAMockups.tsx:34`, `src/pages/pitch.astro:76`), so the cycle is genuinely unimplemented (not a no-op).

### Existing Patterns to Follow
- **Pure-core / thin-wrapper split**: every action helper has a pure builder that totally validates BEFORE producing any plan (throws synchronously on bad input, writing nothing) and a thin async wrapper that routes the dual-write through `writeEvent`. See `buildResourceQueue`→`queueResource` (`src/lib/sessions.ts:860`,`:940`) and `buildQuestionAnswer`→`answerQuestion` (`src/lib/sessions.ts:695`,`:741`). `buildResourceActivate`/`activateResource` must mirror this exactly.
- **Teacher-role validation in the builder**: `buildResourceQueue` checks `input.actor?.role !== 'teacher'` then a present `actor.id` (`src/lib/sessions.ts:861`–`:864`); `buildQuestionAnswer` checks `input.actor.role !== 'teacher'` (`src/lib/sessions.ts:700`). The SPEC requires `buildResourceActivate` to require `actor.role: 'teacher'`, present `userId`/`sessionId`/`resourceId`, and a resource that belongs to the session with a non-blank URL.
- **`record.id === meta.payload.id` keyed-fold consistency**: builders set the payload id equal to the record/projection key so the event folds cleanly (`buildResourceQueue` at `src/lib/sessions.ts:887`). The `ResourceActivated` payload should carry the session id and the resource id + derived `currentUrl` for the fold.
- **Envelope `actor.role: 'teacher'` is hard-set in `meta`** regardless of input shape (`src/lib/sessions.ts:889`, `src/lib/sessions.ts:717`).
- **Default projection-txn helper + injectable `deps`**: wrappers accept `{ write?, buildTxn? }` deps for unit-testing without a network; the real txn is a `defaultXxxTxn` exported function (`defaultResourceTxn` at `src/lib/sessions.ts:904`, `defaultQuestionAnswerTxn` at `src/lib/sessions.ts:729`). The activation txn is a keyed `db.tx.sessions[id].update({ activeResourceId, currentUrl })` — the lifecycle pattern `db.tx.sessions[plan.sessionId].update(plan.update)` at `src/lib/sessions.ts:250` is the closest template (a plain keyed `sessions` update, no link needed since the session row already exists).
- **applyEvent fold convention**: each case spreads the prior projection, reads `event.payload` with a typed cast + defensive defaults, tolerates an absent prior session/row, is keyed defensively (`p.id ?? event.id`), never mutates input, and re-folding reproduces the same entry. The lifecycle cases that mutate the existing session row (`SessionStarted`/`SessionEnded` at `src/lib/db.ts:311`,`:321`) build a minimal session from the payload when `projection.session` is absent — this is the template for `ResourceActivated` (which sets `activeResourceId`/`currentUrl` on the session). The `default` case throws `UnknownEventTypeError` (`src/lib/db.ts:486`), so the new type MUST be added to the switch or `rebuildSessionProjection` breaks.
- **Live-query realtime, no polling**: all views derive state from `db.useQuery` subscriptions (`src/components/SessionLifecycle.tsx:63`, `src/components/StudentSession.tsx:16`). Activation propagation comes free from re-rendering on the live `sessions` row; the student `ResourcePane` needs the active resource's URL — reachable either from a new `currentUrl` scalar on the session row, or by resolving `activeResourceId` against a `sessionResources` query. The SPEC stores `currentUrl` on the session precisely so the pane can render from the single session row.
- **Component query-error / empty-state convention**: query errors are `console.error`'d with a `[ComponentName] …` prefix and never swallowed (`src/components/SessionLifecycle.tsx:92`–`:94`, `src/components/StudentSession.tsx:25`–`:26`); an errored query renders an inline alert checked BEFORE the empty state (`src/components/SessionLifecycle.tsx:441`). Empty states are explicit testid elements, never blank regions (`resource-queue-empty` at `src/components/SessionLifecycle.tsx:457`). The SPEC requires both panes to render an explicit "no active resource" element when nothing is active.
- **Failure handling (action layer)**: builders throw synchronously before any write; wrappers do not catch a rejecting `writeEvent` — the rejection propagates (`queueResource` has no try/catch, `src/lib/sessions.ts:940`). A rejected `db.transact()` fails atomically (single transaction in `writeEvent`, `src/lib/db.ts:577`), leaving no partial state.
- **Failure handling (component layer)**: the teacher action handlers set an inline `role="alert"` error string AND `console.error('[SessionLifecycle] …')`, retaining inputs, with a per-action pending latch; never swallowed (`addResource` at `src/components/SessionLifecycle.tsx:108`, `markAnswered` at `src/components/SessionLifecycle.tsx:172`, `run` at `src/components/SessionLifecycle.tsx:209`). The Activate handler must follow this exact shape (inline `role="alert"` + console.error + pending latch).
- **Observability / event spine**: every product mutation appends a `sessionEvents` envelope via `writeEvent` (`src/lib/db.ts:540`), which stamps `id`/`occurredAt`/`receivedAt`/`schemaVersion` and validates `actor.role` against `ACTOR_ROLES` (`src/lib/db.ts:29`) before the single `db.transact`. Engine-level observability is the append-only `sessionEvents` log queried by admin in e2e (no separate metrics). Cycle-flow events are logged to `.cycle/log.jsonl` by the engine, not by product code.
- **Idempotency / retry-safety**: `writeEvent` is "not idempotent by design" (`src/lib/db.ts:563` comment). Retry-safety for state transitions comes from a guard fed the LIVE state — e.g. `assertLegalTransition` fed the current status (`src/lib/sessions.ts:166`, used by `buildSessionStart`), and `buildQuestionAnswer`'s already-answered guard (`src/lib/sessions.ts:704`). Activation has no SPEC-mandated dedup guard for re-activating the same resource (re-activation simply re-sets the same projection values — a convergent keyed update; switching to a different resource is the primary case). The builder's belonging/role checks are the admission gate.
- **Ownership-in-depth**: enforced both in the builder (role/actor check) AND by the data-layer `sessions` owner-only-write rule (`src/lib/perms.ts:63`, `auth.id == data.teacherId`). The cycle explicitly makes no perms change.
- **Privacy**: no email is ever read or rendered; participant/session/resource rows carry no `email` field structurally (`src/lib/db.ts:88` comment). The pane and activation surfaces render resource/session fields only.

## Open Questions
- **Active-resource indication / testids**: the SPEC mandates "the currently-active resource visibly indicated" and fixed testids for the pane, the Activate control, and the empty state, but does not enumerate the exact testid strings or the active-row marker (e.g. a `data-active` attribute vs. an `activate`-button disabled state). The plan must fix these so the e2e spec and component agree.
- **Student pane data source**: whether the student `ResourcePane` renders from the session row's new `currentUrl` scalar alone (no `sessionResources` query needed in `StudentSession`) or resolves `activeResourceId` against a `sessionResources` query. The SPEC stores `currentUrl` on the session to enable the former; the plan should confirm `StudentSession` reads `currentUrl` from its existing session query rather than adding a resources query.
- **iframe `sandbox` attribute set**: the SPEC requires a controlled/sandboxed iframe "no `allow-same-origin`+`allow-scripts` escalation beyond what embedding requires" but does not pin the exact `sandbox` token list. The plan must choose the concrete sandbox flags.
- **Re-activation guard**: the SPEC does not mandate a dedup/no-op guard for re-activating the already-active resource (unlike the lifecycle/answer guards). The plan should decide whether re-activation appends a second `ResourceActivated` event (convergent keyed update) or is guarded against, consistent with the "not idempotent by design" `writeEvent` stance.
