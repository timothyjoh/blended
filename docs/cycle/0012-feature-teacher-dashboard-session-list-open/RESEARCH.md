# Research: Cycle 0012

## Cycle Context
SPEC.md asks for a new realtime, owner-scoped session list on the teacher `/dashboard`. A new `SessionList` island must mount inside the existing `RouteGuard` on `/dashboard` (beside the already-mounted `NewSession`), run a `db.useQuery` over the `sessions` projection filtered server-side to the signed-in user's owned rows (`where: { teacherId: user.id }`), render each session's title and current status (`draft`/`live`/`ended`) ordered stably client-side, and link each row to the existing facilitation route `/dashboard/sessions/:id`. The list must reflect InstantDB changes (creation, status transition) in realtime with no polling, and must surface explicit loading, empty, and error states (inline `role="alert"` + `console.error('[SessionList] …')`), passing `null` to `db.useQuery` when the user id is unresolved. No schema change, no permission-rule change, no `instant-cli push` is in scope (the `sessions` entity, its `teacherId` field, and its open-read/owner-only-write rules already exist).

## Open Questions
- **Comparator extraction location/name**: SPEC §117-118 wants the stable ordering comparator (and any title/status display fallback) extracted as pure, testable logic beside the module as `*.test.ts`. The codebase has no existing shared comparator (it is inlined in `SessionLifecycle` and `StudentChat`); the plan must decide whether the new pure helper lives in `src/lib/sessions.ts`, a new module, or co-located beside `SessionList`, and whether to refactor the two existing inline copies (the SPEC scopes the extraction to SessionList only).
- **Title fallback placeholder text/testid behavior**: SPEC §94 requires a row with a missing title to fall back to a non-blank placeholder; the exact placeholder string is unspecified (sibling precedent: `'(question text unavailable)'` at `src/components/SessionLifecycle.tsx:256`).
- **Row navigation mechanism**: SPEC requires a navigation affordance to `/dashboard/sessions/:id`; whether each row is an `<a>` (precedent: `src/components/NewSession.tsx:115`) or a button using `window.location` is a plan decision — the SPEC fixes the testids (`session-list-item` with `data-session-id`, `session-list-item-title`, `session-list-item-status`) but not the element type.
- **Loading vs. unresolved-auth states**: SPEC distinguishes the query-loading state (`session-list-loading`) from the unresolved-user-id case (render nothing actionable, pass `null` to `db.useQuery`). The plan must define how the island renders before `user?.id` resolves vs. while the live query is in flight, mirroring the `SessionLifecycle` loading early-return.
