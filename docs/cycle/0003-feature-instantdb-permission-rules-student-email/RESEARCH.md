# Research: Cycle 0003

## Cycle Context
SPEC.md asks this cycle to author, commit, and push a single InstantDB permission-rules artifact (`instant.perms.ts`) that moves two spec-mandated security invariants from convention/UI into the data layer: (1) **student email privacy** — a participant's/user's `email` is readable only by that user, never by other students; and (2) **session-state write authorization** — only the owning teacher (plus a reserved system/admin path) may create/mutate `sessions` and `sessionResources` rows, while any authenticated participant may still append to the append-only `sessionEvents` log. The rules must be pushed to the live Instant app via `npx instant-cli push perms`, documented in `AGENTS.md`, must not break the cycle-0002 auth flow / first-sign-in `users`-row creation / the `/dev/event-spine` harness, and must be proven by a new Playwright spec (`e2e/permissions.spec.ts`) that signs in a teacher and a student deterministically via the admin SDK. Since the `sessionResources.sessionId` is a plain indexed string (not a traversable link), the cycle may add the minimal mechanism (an InstantDB link to `sessions`, or a denormalized owner id) needed to make resource ownership checkable in a rule.

### Existing Patterns to Follow
- **Single-source modules**: the schema and client live in exactly one module (`src/lib/db.ts`); ADR-0001/0003 and AGENTS.md forbid re-declaring schema or calling `init()` elsewhere — `AGENTS.md:13`. A new `instant.perms.ts` would be the analogous single source for permission rules.
- **Dual-write choke point**: all product mutations go through `writeEvent(type, meta, projectionTxns)`, which appends a `sessionEvents` envelope **and** the caller's projection update(s) in one `db.transact()` — `src/lib/db.ts:279-317`. First-sign-in `users` creation routes through it under `IDENTITY_SCOPE` with actor role `'unknown'` and a `UserSignedIn` event — `src/lib/useAuth.ts:61-86`. Any perms rule on `users`/`sessionEvents` must keep this write path legal.
- **Validate-before-write / throw-not-swallow**: `writeEvent` validates all input synchronously and throws before issuing any transaction, writing nothing on invalid input — `src/lib/db.ts:284-300`. `requireAppId` throws at init rather than building a broken client — `src/lib/db.ts:17-24`. This "fail loudly, never silently degrade" convention is the model the SPEC's "push must fail loudly with non-zero exit" requirement mirrors.
- **Failure handling**: rejected transactions propagate to the caller and are surfaced, never swallowed — `useAuth` logs and re-attempts on next resolution (`console.error('[useAuth] users row creation failed:', …)`) — `src/lib/useAuth.ts:77-85`; the harness `surface()` sets visible error state and `console.error`s — `src/components/EventSpineHarness.tsx:101-105`. Because event+projection share one transaction, a rejection is atomic (no half-applied dual-write) — `src/lib/db.ts:268-276,315-316`.
- **Observability**: the structured engine log is `.cycle/log.jsonl` (newline-delimited JSON events: `cycle.start`, `step.start/end`, `step.completion_check`, `cycle.noop`, etc.). In product code, observability is the append-only `sessionEvents` log itself (ADR-0003 internal observability) plus `console.error` on the failure paths above. There is no metrics/telemetry layer.
- **Idempotency / retry-safety**: first-sign-in creation is guarded by `shouldCreateUserRow` (auth id present, query loaded, zero existing rows, no in-flight write) plus an `inFlight` ref, and the `users` row is keyed to the auth id so duplicate effects resolve to one row — `src/lib/auth.ts:47-55`, `src/lib/useAuth.ts:35-86`. `writeEvent` is explicitly **not** idempotent (each call appends a fresh event) but atomicity makes a caller retry safe — `src/lib/db.ts:271-276`. The engine itself uses lock files (`.cycle/engine.lock`, `.claude/scheduled_tasks.lock`).
- **Auth state flows through one hook**: product code MUST NOT call `db.useAuth()` directly — `AGENTS.md:19`, `src/lib/useAuth.ts:11-17`.
- **Code style**: modern TS/JS, **no semicolons**, two-space indent — `AGENTS.md:9-10`.

## Open Questions
- **Perms-push prerequisites**: `npx instant-cli push perms` conventionally reads `instant.perms.ts` (and may require an `instant.schema.ts`) from the project root, but the schema currently lives only inline in `src/lib/db.ts` and no `instant.schema.ts` exists. The plan step must determine whether pushing perms requires generating/committing an `instant.schema.ts` (or otherwise reconciling the CLI's expectations with the single-source-in-`db.ts` convention), and how `instant-cli` authenticates (env token vs. interactive login) so the push can "fail loudly with non-zero exit."
- **`sessionResources` ownership traversal**: the SPEC authorizes adding the minimal mechanism (an InstantDB link `sessionResources → sessions`, or a denormalized owner/`teacherId` field on the resource row) to make ownership checkable in a rule. The plan must pick one and decide its impact on the `writeEvent` call sites that will later create resource rows.
- **System/admin write path expression**: how an InstantDB permission rule references `User.adminLevel` (which lives on the `users` namespace keyed by `auth.id`) — e.g. via `auth.ref` against a link to the `users`/`$users` namespace — to reserve the admin/system write path without building admin UI this cycle.
- **Dev-harness compatibility under auth-gated rules**: `EventSpineHarness.tsx` writes `sessions`/`participants` from an unauthenticated context with literal ids (`teacherId: 'dev-teacher'`); the SPEC requires the `/dev/event-spine` harness to keep working under the new rules. The plan must reconcile owner-only `sessions` write rules with this unauthenticated harness path (e.g. scope, exemption, or harness sign-in).
- **First-sign-in `users` write rule**: the rule restricting `users` reads to `auth.id == data.id` must still permit a user to **create/update their own** `users` row on first sign-in (`db.tx.users[authUserId]` under `IDENTITY_SCOPE`); the create vs. view rule split needs to be defined so cycle-0002 auth is not broken.
