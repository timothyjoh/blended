# Research: Cycle 0019

## Cycle Context
SPEC 0019 turns the dormant `users.adminLevel` placeholder into a trustworthy, unforgeable global capability and ships the first vertical slice of admin access end-to-end. It requires: (1) modeling `adminLevel` as the named domain union `'none' | 'uber'` (schema field change from `i.number()`), with pure helpers in a new `src/lib/admin.ts` (`ADMIN_LEVEL_NONE`/`ADMIN_LEVEL_UBER`, `AdminLevel`, `normalizeAdminLevel`, `parseAdminEmails`, `isEmailAllowlisted`); (2) a server-only `POST /api/admin/bootstrap` endpoint that verifies the caller's InstantDB token via `@instantdb/admin`, and — only when the verified email is in the server-only `ADMIN_EMAILS` allowlist and the user is not already `uber` — atomically sets `adminLevel: 'uber'` and appends an `AdminBootstrapped` event under `IDENTITY_SCOPE` (bypassing permission rules); (3) `useAuth` calling that endpoint once per authenticated session (ref-latched/idempotent); (4) tightening the `users` permission rule so a client can never write a non-`'none'` `adminLevel`; (5) a pure `authorizeAdmin` helper in `src/lib/routing.ts`, an `AdminRouteGuard` island mirroring `SessionRouteGuard`, and an `/admin` Astro page gated by it; (6) extracting a shared pure `buildEventEnvelope(type, meta)` from `writeEvent` so the client and the server endpoint emit identical §7.2 envelopes; (7) unit + e2e tests including failure paths; and (8) documentation updates to AGENTS.md, README.md, .env.example.

## Current Codebase State

### Existing Patterns to Follow
- **Pure-core + co-located-test split**: domain logic lives as pure, total functions in `src/lib/*.ts` (never touching DOM/`window`/InstantDB) with co-located `*.test.ts`; `.tsx` islands stay outside unit scope. Stated in `src/lib/routing.ts:1-9` and `src/lib/auth.ts:1-5`. `src/lib/admin.ts` must follow this.
- **Total helpers (hostile input → safe default, never throw)**: `safeNextPath` (`src/lib/routing.ts:21-27`), `deriveUsername` (`src/lib/auth.ts:35-39`), `authorizeOwnership` (`src/lib/routing.ts:43-53`). `normalizeAdminLevel`/`parseAdminEmails`/`isEmailAllowlisted`/`authorizeAdmin` must be total in the same style.
- **`AuthzDecision` verdict ordering**: error wins over loading, then missing inputs → `denied`, else compare — `src/lib/routing.ts:49-52`. SPEC requires `authorizeAdmin` to match this exactly (error → `denied`; loading → `loading`; `authorized` only when `normalizeAdminLevel(adminLevel) === ADMIN_LEVEL_UBER`).
- **Precomputed-decision guard wrapper**: a `*RouteGuard` island runs the `db.useQuery` (hooks can't be conditional inside a predicate closure), folds through the pure helper, passes `authorize` to `RouteGuard` — `src/components/SessionRouteGuard.tsx:24-38`. `AdminRouteGuard` reads the signed-in user's OWN `users` row: the existing own-row query pattern is `db.useQuery(authUserId ? { users: { $: { where: { id: authUserId } } } } : null)` — `src/lib/useAuth.ts:40`.
- **Null-guarded query until id resolves**: `db.useQuery(id ? {…} : null)` so InstantDB skips the query when signed out — `src/lib/useAuth.ts:40`, `src/components/SessionRouteGuard.tsx:25`.
- **Astro page mounts a guard around `client:only="react"` islands**: `src/pages/dashboard/sessions/[id].astro:16-22` (wraps `SessionLifecycle` in `SessionRouteGuard`); `src/pages/dashboard/index.astro:21-29` (wraps content in `RouteGuard`). The new `/admin` page mirrors this with `AdminRouteGuard` and a `data-testid="admin-root"` child.
- **Single auth seam**: identity is read exclusively through `useAuth` (`src/lib/useAuth.ts`), never `db.useAuth()` directly — enforced convention (AGENTS.md:31, `src/components/RouteGuard.tsx:27`).
- **Ref-latched idempotent side effect in `useAuth`**: the `inFlight` ref + `shouldCreateUserRow` gate prevent double-fire of the first-sign-in write — `src/lib/useAuth.ts:35,45-86`; `shouldCreateUserRow` is the pure gate at `src/lib/auth.ts:47-55`. The bootstrap call ("once per authenticated session, ref-latched, idempotent") should follow this latch pattern.
- **Schema-string-union enum convention**: typed enums expressed as `i.string<Union>()` (e.g. `status: i.string<'draft'|'live'|'ended'|'archived'>()` — `src/lib/db.ts:50`). The `adminLevel` change should follow this (`i.string<AdminLevel>()` or `i.string<'none'|'uber'>()`).
- **Failure handling (current conventions)**:
  - `writeEvent` validates ALL input synchronously and throws BEFORE issuing any transaction; the append + projection share one transaction so a rejection is atomic and propagates to the caller, never swallowed — `src/lib/db.ts:673-705`.
  - Side-effect callers `.catch` and `console.error` with a `[Component] …` prefix, never crash the app: `useAuth` first-sign-in write — `src/lib/useAuth.ts:77-82` ("Surface, never swallow"); guards log via `console.error('[RouteGuard] …')` / `console.error('[SessionRouteGuard] …')` — `src/components/RouteGuard.tsx:49`, `src/components/SessionRouteGuard.tsx:28`. SPEC's client-side bootstrap failure path ("logged via `console.error`; degrade to non-admin") matches this convention.
  - Server endpoint guards return explicit `Response` status codes (e.g. `404` outside DEV) — `src/pages/e2e/hang.ts:19-20`. SPEC requires the bootstrap endpoint to return `401` (bad/missing/expired token), `500` (admin SDK unavailable / `INSTANT_ADMIN_TOKEN` unset), `200` (verified-but-not-allowlisted → `adminLevel: 'none'`, no writes).
  - `RouteGuard` never collapses an error to "authenticated": auth error → `route-guard-denied` (`src/components/RouteGuard.tsx:48-55`); loading never redirects, preventing flash-redirect (`src/components/RouteGuard.tsx:31-44,59-65`). The `/admin` route reuses these loading/denied shells (testids `route-guard-loading`, `route-guard-denied`).
- **Observability conventions**: every mutation is an append-only `sessionEvents` envelope written through `writeEvent`; the §7.2 envelope shape stamps `id`, `sessionId`, `type`, `schemaVersion` (default `1`), `actorId`, `actorRole`, `occurredAt`, `receivedAt`, optional `correlationId`, `payload` — `src/lib/db.ts:691-702`. Identity-scope events use `sessionId: IDENTITY_SCOPE` with `actor.role: 'unknown'` — `src/lib/useAuth.ts:63-65`. `AdminBootstrapped` is to be a new identity-scope event, appended via the shared envelope, and (like `UserSignedIn`) intentionally not folded by `applyEvent`. There are no metrics/structured-log systems beyond the event spine and `console.error`.
- **Idempotency / retry-safety mechanisms**: `writeEvent` is "not idempotent by design" (each call appends fresh) but atomic, so retry is safe — `src/lib/db.ts:660-666`. Keyed upserts give convergence (the `users` row id IS the auth id — `src/lib/useAuth.ts:69`, perms note `src/lib/perms.ts:44-47`). The bootstrap endpoint's idempotency must come from an explicit guard ("only when not already `uber`"); the client call from a ref-latch (cf. `inFlight` — `src/lib/useAuth.ts:35`).
- **Admin SDK bypasses permission rules**: documented in `src/lib/perms.ts:11-13,62-63,82-84` and AGENTS.md:26 — the elevated write MUST use `@instantdb/admin` so the tightened `users` rule (which forbids client elevation) does not block the server.

### Dependencies & Integration Points
- **`@instantdb/admin`**: currently a **devDependency** (`^1.0.43`), NOT a runtime dependency (`@instantdb/react ^1.0.43` is the runtime dep). It is used today only by Node-side scripts and the e2e seam — `e2e/support/auth.ts:1,24-28,44-48` (`init`, `auth.generateMagicCode`, `admin.query`). The new `/api/admin/bootstrap` server route would `init({ appId, adminToken })` and call token-verification + rule-bypassing writes via this SDK at runtime. (SPEC asserts it is "already a dependency"; it is present in `devDependencies` only — a planner must confirm runtime availability under the Vercel build.)
- **InstantDB token verification**: the admin SDK exposes `admin.auth` (used for `generateMagicCode` in e2e — `e2e/support/auth.ts:28`); SPEC relies on its token-verify method to validate the caller's InstantDB token server-side.
- **Server env vars**: `INSTANT_ADMIN_TOKEN` (server/Node-only, e2e today — `e2e/support/auth.ts:15,26`, AGENTS.md:67) and the new server-only `ADMIN_EMAILS` (no `PUBLIC_` prefix). The `.env.example` currently lists only `PUBLIC_INSTANTDB_APP_ID` and `INSTANT_ADMIN_TOKEN` — `.env.example:1,7`.
- **`useAuth` ↔ bootstrap endpoint**: `useAuth` (`src/lib/useAuth.ts:32`) is the integration point that will `fetch` the endpoint once per authenticated session; it already exposes the auth user and runs the own-`users`-row query (`src/lib/useAuth.ts:33,40`).
- **Schema + perms push tooling**: `npm run perms:push` → `scripts/push-perms.mjs` → `npx instant-cli push perms` (loads root `instant.perms.ts` adapter which re-exports `src/lib/perms.ts` — `instant.perms.ts:5`). - **`AuthGate` / `/login`**: product sign-in surface (`src/pages/login.astro` → `src/components/AuthGate.tsx`, AGENTS.md:31). The e2e bootstrap path drives this via `signInViaUi` — `e2e/support/auth.ts:58-71`.

## Open Questions
- **`@instantdb/admin` runtime availability**: the SDK is currently a *devDependency* only (`package.json` devDependencies, `^1.0.43`), but `/api/admin/bootstrap` imports it at runtime under the Vercel server build. Does it need to move to `dependencies`, and is the Vercel adapter bundling configured to include it? (Resolve in plan.)
- **Exact admin-SDK token-verification API**: the precise method/signature for verifying a caller's InstantDB token server-side (the SPEC names "verifies the caller's InstantDB token via the admin SDK") is not yet exercised anywhere in the repo — only `generateMagicCode`/`query` are used (`e2e/support/auth.ts`). The plan must confirm the verify call and its error shape (to map to `401`/`500`).
- **Server-side env access for `ADMIN_EMAILS`/`INSTANT_ADMIN_TOKEN` inside an Astro API route**: existing server code reads `import.meta.env.DEV` (`hang.ts`) while Node/e2e reads `process.env` (`auth.ts`); which accessor is correct/reliable for secrets in a Vercel-adapter Astro `APIRoute` (and which keeps `ADMIN_EMAILS` out of the client bundle) needs confirmation.
- **How `useAuth` obtains the caller token to send to the endpoint**: the mechanism by which the client passes a verifiable InstantDB token to `/api/admin/bootstrap` (e.g. a refresh/access token from the InstantDB auth surface) is not present in current `useAuth` code (`src/lib/useAuth.ts`).
- **`AdminBootstrapped` envelope `actor.role` and `payload` shape**: SPEC fixes the scope (`IDENTITY_SCOPE`) and type but the exact `actor.role` (presumably `'unknown'`/`'system'`, both valid `ACTOR_ROLES` — `src/lib/db.ts:29`) and payload fields are to be finalized in the plan.
- **e2e idempotency assertion against a shared live app**: SPEC wants a deterministic allowlisted email (`admin@blended.test`) added to `ADMIN_EMAILS`; because the live Instant app is shared and `users` rows persist by auth id, the "second call writes no new event" assertion may interact with prior runs — the plan should define how the e2e isolates or tolerates pre-existing `uber` state.
